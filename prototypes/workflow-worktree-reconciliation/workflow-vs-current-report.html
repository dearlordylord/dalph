Effect Workflow vs current Dalph worktree recovery · disposable experiment

Workflow replays a result.
Dalph still owns recovery.

● No-go

Do not adopt Effect Workflow for worktree reconciliation, and stop further Workflow evaluation. The prototype preserved the required recovery behavior, but it did not make Dalph’s existing restart procedure deletable. It added a second durable store and more identity, schema, fault, inventory, and test machinery around responsibilities that remain necessary.

Observed testSource inspectedDecision judgment

Workflow helped

Stored Activity result replay

After the result was durably stored, restart returned it without another controlled Git call. That is real leverage, demonstrated under SIGKILL.

Workflow did not replace

Authority and restart procedure

Git still resolves ambiguous creation and supplies current truth. The Journal still accepts Run chronology. Outer Dalph code still rereads, publishes, folds, and gates the next decision.

Action

Retain the current design

Keep recoverTaskWorktreeOperation, the controlled read/create/reread protocol, Journal intent/outcome publication, and process-local runtime. Do not prototype promotion or integration as a successor.

Concrete chronology before terminology

What happened at each crash boundary

No person or live provider acted. A parent harness killed a real Node child; a controlled Git adapter represented outside facts. The same Run, Attempt, operation, Base SHA, branch, locator, Workflow execution, and Activity identity crossed restart.

Creation applied; Activity result was not stored

Ambiguous external effect

  2. Git read: absent
  3. Create applied once
  4. SIGKILL before result storage
  5. Restart rereads Git: ready
  6. Journal records one ready outcome

Current Dalph responsibility

Read the retained intent, invoke the existing reconciliation protocol, and let Git settle ambiguity by rereading before another create.

Workflow candidate contribution

The Activity restarted because no result was stored. It still had to call the same Git reconciliation protocol. Workflow alone did not prevent duplication.

Visible evidence: one create, three reads, one intent, one ready outcome, no executor contact, no physical worktree. The blind-retry control created twice. Acceptance test, lines 25–94.

Activity result stored; Journal outcome not published

Durable replay leverage

Observed test
  1. Git read: absent
  2. Create then reread: ready
  3. Workflow stores Activity result
  4. SIGKILL before Journal append
  5. Restart replays; no Git call
  6. Journal append removes proposal

Current Dalph responsibility

Recover the acknowledged intent, execute the named protocol, and append the outcome through the ordinary Journal path. Idempotent Journal keys prevent duplicate accepted outcomes.

Workflow candidate contribution

Replayed the stored result without repeating the controlled Git Activity. Outer Dalph code still appended, reread, reduced, and published the Journal state.

Critical distinction: the Workflow record proved a past Activity return. Only Journal publication advanced delivery. Suppressing that append left the proposal present. Acceptance test, lines 96–129 and 173–194.

3

Controlled Git facts changed during downtime

Historical proof is not current authority

Observed test
  1. Activity stored ready result
  2. SIGKILL before Journal
  3. Downtime: Git becomes absent
  4. Workflow replays past ready
  5. Journal accepts past occurrence
  6. Fresh Git read says wait

Current Dalph responsibility

Before executor admission, read Git again. The owner of worktree facts reported absent, so Dalph waited/fail-closed and made zero executor calls.

Workflow candidate contribution

Correctly replayed history, but could not authorize the present decision. The negative control that treated replay as current truth incorrectly continued.

Result: the authority rule survives unchanged: copied external facts do not become current authority. Acceptance test, lines 131–154 and 196–214.

Issue #234 deletion test

The candidate adds more recovery surface than it removes

This ledger counts responsibilities and concepts, not raw lines. The question is whether a production recovery duty becomes demonstrably deletable.

Removed inside handler

Workflow kept narrow

  • Proposal construction
  • Graph/relation construction
  • Journal append
  • Current-decision read
  • Signal update

These were excluded from the Workflow handler, not deleted from Dalph overall.

Retained

Core recovery duties

  • Restart dispatcher and intent lookup
  • Git read/create/reread
  • Journal intent/outcome
  • Exact resource qualification
  • Fresh-current-fact gate
  • Runtime and Application Exit
Added

Workflow machinery

  • Execution SQLite store
  • Payload/result schemas
  • Stable Workflow/Activity identity
  • Typed error transport
  • Runner and fault hooks
  • Row-level inventory and ledgers
Duplicated

Recovery vocabulary

  • Worktree recovery in Activity and outer seam
  • Journal reconstruction around replay
  • Exact identity across two histories
  • Evidence around production projection

Code shape

Current: recovered route → recoverTaskWorktreeOperation → retained intent lookup → interpreter → Git protocol → Journal trace/publication.

Candidate: ordinary planning → DeliveryActionExecutor → exact Workflow execution → Activity → same Git protocol → return to outer executor → Journal append/reduce → fresh Git decision.

Locality and test surface

The candidate’s adapter is injectable, but identity, fault hooks, replay evidence, Journal folding, projection evidence, storage inventory, and current-decision evidence cross seven prototype modules. Nine focused tests and multiple extra ledgers are necessary to prove the new boundary did not become a second authority.

Identity path across the recovery seams

  1. Parent harness → first and second child: the parent passes the exact Run and controlled workspace, then rejects any ChildReady message whose Run, Operation, Attempt, Base, branch, locator, or Activity differs. harness.ts:43–78, 97–118, 151–197.
  2. Both children → Workflow payload: the exact Run, Attempt, Operation, Base, branch, locator, and scenario form the typed payload; the Run supplies the idempotency key. workflow-reconciliation.ts:185–201, 458–466.
  3. Workflow payload → Activity evidence: Activity evidence stores those exact identities plus the Workflow-generated execution ID. contracts.ts:87–109.
  4. Activity → controlled Git ledger: every read/create entry carries Run, Attempt, Operation, Base, branch, locator, and child process instance. contracts.ts:62–85.
  5. Workflow result → Journal event: outer executor code appends the exact Operation and controlled proof as one TaskWorktreeReady, then folds the Journal before publication. workflow-reconciliation.ts:485–513; test:58–69.

Glossary

Activity result
The typed result Effect Workflow stores and may replay. It describes what the controlled adapter returned at an earlier time.
Current authority
A fresh fact from the system that owns it. For worktree readiness, that system is Git—not Workflow or the Journal.
Dalph Journal
The sole accepted, ordered Run chronology. Publication changes ordinary delivery inputs.
Reconciliation
After ambiguity, reread the owning system before deciding whether an earlier request may be continued or repeated.
Deletion leverage
Recovery responsibility and conceptual/test surface that can actually be removed because Workflow supersedes it.
Process-local runtime
Planning, admission, live ownership, and current signals rebuilt from accepted history and current facts; never durable authority.
