# Start independently owned Codex processes in one provider home

Issue: [#431](https://github.com/dearlordylord/dalph/issues/431).

Status: accepted startup direction and chronology; tests below declare implementation seams. The maintainer confirmed that authentication coordination will be specified separately; #431 delivers the agreed startup boundary and reports the demonstrated managed-refresh limitation.

## Governing behavior

Dalph gives each exact executor attempt and integration session its own app-server and custody under [isolated containment](isolated-codex-containment.md). This refines initialization only. Existing stop, notification, completion, fixed Exit drain, tracker claims, Git candidates, and journal authority remain intact. Startup admission is a local cooperative OS boundary over one canonical home, released after initialization, not ownership of that home or of another unit's process.

The [planned-attempt boundary](planned-attempt-executor-boundary.md) and `plannedAttemptExecutor.everyCallHasOneDurableIntent` / `plannedAttemptExecutor.beginTurnCrossesAtMostOnce` in [its model](../../specs/plannedAttemptExecutor.qnt) continue to govern workflow calls. [Preservation](../DELIVERY-INVARIANTS.md#preservation), [ambiguity and evidence](../DELIVERY-INVARIANTS.md#ambiguity-and-evidence), and [process durability](../DELIVERY-INVARIANTS.md#process-and-durability) prohibit inferred replacement or release. Startup admission adds no generic executor report or workflow identity.

## S1: Ordinary and explicit provider homes reach every owned child

The maintainer has configured a repository, claims, capacity, deterministic worktrees and private executor/integrator state. No owned process has started. An ordinary host configuration omits codexHome; another configuration supplies one absolute provider-home path, possibly through a symlink alias. Dalph resolves the effective ordinary home or explicit path at its native configuration boundary, binds its canonical namespace in the unit's private execution record, and passes that exact home only to independently owned executor, integrator and recovery children. It never copies credentials, changes ambient config, or writes startup records into the provider home. The maintainer sees normal startup or a typed configuration failure before process effects.

A crash between namespace binding and launch leaves no permission to choose another namespace. Recovery reuses the binding; a changed ambient/explicit namespace or unprovable legacy binding refuses admission before spawn. An exact redelivery reuses the record. Claims, Git refs and planned Bases do not change: provider selection grants no workflow authority.

Tests to add: configuration accepts omitted/explicit codexHome; exact executor and integrator launch environments use canonical explicit home; ordinary home remains separate and unchanged; recovery preserves the original home; changed/unknown retained home refuses before effects.

## S2: Same-home initialization is serialized and active owners remain parallel

Attempts A and B and an integration session are independently admitted under bounded capacity, with their own stores and exact worktrees. Each resolves the same canonical home, including aliases. Before waiting Dalph records each startup identity, namespace and original absolute deadline, thirty seconds from that startup intent. It takes cooperative startup admission for A, records launch intent, starts A's exact process, observes its identity, and sends initialize. B and integration wait without spawning. After A's valid initialize response, Dalph records observed initialization and releases admission; B and then integration can initialize. A remains live and executes ordinary RPCs while B initializes. A different home does not wait on this admission.

The maintainer sees independent providers with at most one simultaneous same-home initialize. No home-lifetime lease, shared daemon, task position reassignment, tracker mutation or publication is authorized. A crash at any intent/observation boundary follows S4; redelivery never duplicates a pending startup or extends its deadline.

Tests to add: exact same-home/alias initialize barrier across processes; independent-home initialization overlaps; initialized A serves thread/turn calls while B initializes; integrator participates in the same queue and retains its independent session.

## S3: Queue timeout never spawns or stops siblings

A owns same-home startup admission; B has persisted its original deadline and has not spawned. Time passes until B's thirty-second deadline. Dalph returns a typed queue-startup failure and records the no-child disposition for B using its own launch/custody evidence. A remains alive. B's claim, planned worktree, Base and workflow history remain retained; a timeout is not task completion or writer release for an unrelated retained attempt.

If Dalph crashes during B's queue, recovery reads B's original deadline and exact intent before waiting. It cannot create a new thirty-second budget. Redelivery after expiry remains a failure rather than silently spawning. The maintainer sees the exact startup deadline boundary. Retry of ambiguous effects requires S4 reconciliation, and explicit recovery authority remains the separate workflow protocol.

Tests to add: TestClock queue expiry produces zero child starts; restart retains remaining/expired original budget; initialized siblings answer; precise deadline diagnostics omit credentials and authored payloads.

## S4: Lost initialize response and crashes preserve exact custody

A has persisted startup intent and owns admission. Dalph may crash after launch intent but before PID acknowledgement, after observing the exact process identity, while initialize is unanswered, or after receiving initialize but before persisting/releasing admission. Recovery first checks the original deadline and reconciles A's exact prior launch token, process identity and writers. It never guesses a stale PID, signals another unit, or treats an unlocked OS descriptor as proof of writer absence.

An expired initialize closes only A's exact containment and records stopped-writer evidence. Unreadable/contradictory evidence retains the launch and admission fence; no replacement is permitted. If exact absence is proved, a permitted retry before expiry uses the remaining original budget. If valid initialization was durably observed before the crash, release that startup admission without killing a currently live unrelated initialized provider. Later deliberate/new startup after an already completed initialization records a distinct intent; it does not disguise an incomplete startup as new.

The maintainer sees initialized service, typed deadline failure with exact stopped proof, or unresolved custody. Tracker claims, Git candidates and old execution facts remain unchanged. Tests to add: pre-ack launch-token crash; post-spawn lost response; observed-initialize/release crash; failed stop proof retains durable fence; foreign/reused PID stays untouched; same original deadline across restart.

## S5: Complete thread discovery remains required

The integrator retains an exact candidate worktree and a ThreadStartIntentRecorded or CandidateReady record without an acknowledged thread. The provider home contains unrelated histories, multiple pages and possibly a loaded thread without a rollout file; database metadata may be missing or stale. Dalph completes exact provider/cwd-filtered persistent discovery and loaded-thread discovery before interpreting absence. It adopts only the exact owned session under the existing token rules. Foreign histories, mismatched cwd/provider, duplicate eligible sessions or incomplete pages never authorize a new session.

Investigate history enumeration separately from startup SQLite contention. A DB-only empty response cannot prove absence; pinned Codex may return an empty list when database enumeration is unavailable. Any optimization needs a fresh independent complete witness and explicit metadata/loaded-only controls before production selection. If an RPC does not answer, preserve candidate/session and return the safe bounded boundary diagnostic; reconcile before another thread/start. A crash after an ambiguous start retains its original intent and exact owned-session recovery rules.

Existing tests to preserve: `filters every persistent page by exact cwd and merges the complete loaded-thread census`; `rejects an incomplete loaded census after exact-cwd persistent discovery`; `does not retry thread/start after a lost response when candidate census fails`; exact owned-session integrator token cases. Additional seams: absent/stale DB entries cannot fabricate empty custody, all-page provider/cwd filters, loaded-only session, bounded unanswered discovery preserves exact candidate and no second start.

## S6: Exit keeps its original fixed drain

The operator requests Exit while one unit initializes and another waits on its recorded deadline. Dalph closes forward admission once, removes only exact queued ownership, and reconciles/quick-drains only owned initialization resources under the original five-second application Exit deadline. Existing task suspension and integration atomic-action rules remain unchanged. It never gives startup its own extra thirty-second Exit drain, starts the queued unit after Exit, stops a sibling as a substitute for custody proof, or deletes the shared home.

A crash during Exit does not persist an Exit mode in the Run journal; ordinary recovery reconciles startup/launch intent and stopped writers. The maintainer sees the existing Succeeded/Failed/TimedOut Exit result with truthful custody. Tests to add: queued and initializing provider host Exit; no post-Exit spawn; original drain bound and precise unresolved owner retained.

## S7: Qualification reports sustained activity and managed refresh truthfully

Short successful turns do not prove sustained tools or concurrent managed refresh. Minimal real pinned Codex processes in a synthetic fixture must perform multiple turns and tool activity with independent exact threads and readback. Authentication fixtures use synthetic credentials and loopback endpoints, never the maintainer's auth files. Concurrent provider-managed refresh is a separate observation from startup serialization. Record successful token rotation or the exact failure and supported limit; do not relabel RPC envelope success as refresh success.

The diagnostic on 2026-10-04 observed duplicate use of a synthetic refresh token by two sequentially initialized same-home servers. One refreshed; the other's successful getAuthStatus envelope contained no token and stderr recorded refresh_token_reused. A subsequent synthetic real-turn diagnostic used two independently initialized pinned app-servers, loopback OAuth and Responses endpoints, and exact independent threads. Both attempted the original refresh token: one turn completed and the other failed. This proves a provider-level concurrent-refresh failure in that controlled setup; it does not qualify full Dalph composition or define new Dalph authentication coordination. The maintainer accepted keeping authentication coordination in a separate specification. No copy-home workaround, user credential mutation, runtime policy restriction or authentication proxy has been authorized by this evidence.
