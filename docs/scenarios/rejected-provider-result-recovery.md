## Common starting facts and authorities

Alice has one admitted task A, an immutable planned attempt P1 on Base H1, its exact owned worktree W1, tracker specification/revision and claim, and provider-owned thread/session S1 and turn T1. Another task B remains blocked by A; rejection, correction and recovery do not satisfy that edge. Git owns HEAD and lineage; the provider/execution substrate owns session and writer facts; the private executor store owns response-cycle facts; the journal owns applied Operator direction and accepted workflow observations. Existing terminal seals remain immutable.

## S1 — Dalph validates a correct owned answer before acceptance

The provider completes T1 with a semantic Accepted proposal containing its commit, without application IDs. Dalph independently proves exact S1/T1 ownership, decodes the payload, reads W1 HEAD, proves candidate lineage from H1 and required evidence, then publishes and reads back its acceptance evidence. It rereads HEAD and proves exact owned activity absent before sealing Accepted. Alice sees ordinary acceptance; integration/publication/tracker completion remain separate and B remains blocked until their normal authority permits it. Crashes before sealing reuse exact turn/evidence observations without duplicate acceptance; after sealing, reread validates the immutable seal. Forbidden: accept a syntactically valid SHA without Git evidence, foreign answer, stale code verification, or release B from mere proposal. Acceptance seams: shared effectful validator tests; existing executor acceptance/evidence readback tests and public blocked-edge scenario.

## S2 — Dalph requests at most two fresh full-access corrections

T1 completes with malformed JSON or a candidate that the full validator rejects. Dalph records the rejection and first correction identity/token/absolute deadline before asking S1 for a new full-access turn. Its instruction contains the exact semantic schema and specific validator feedback, with no model-copied application IDs. The additional response must arrive within its persisted 30 seconds and passes every S1 check against current code. A rejection permits one second correction under another intent and 30-second deadline; acceptance proceeds normally. Alice sees correction progress and count. A crash or exact redelivery retains cycle identity, consumed ordinal and original deadline. Forbidden: retry unchanged bytes, hide Git unavailability as JSON feedback, allocate a fourth response, or credit checks of code subsequently changed. Acceptance seams: controlled correction success/three-response tests with TestClock; provider request assertions; negative controls for deadline/counter reset.

## S3 — Dalph returns an exhausted or expired cycle to Alice with exact custody

The third answer is rejected, or an additional response's original 30-second deadline expires. Dalph records the boundary reason and intent to stop its exact executor, applies #434 process custody, then observes exact thread/process/token-writer absence. Proven absence produces a stopped recoverable rejection retaining W1; incomplete or contradictory evidence produces explicitly unresolved custody and retains the fence. Alice sees reason, consumed corrections, retained candidate/worktree, proof state and admissible recovery. Crashes between stop intent, stop effect and absence observation reconcile the same owner before retry. Forbidden: semantic Failed seal for boundary rejection, timeout-derived safe capacity, automatic replacement, foreign process termination. Acceptance seams: controlled exhaustion/deadline tests; one minimal native exact-cleanup scenario and unresolved-writer negative control.

## S4 — Alice explicitly Continues retained work with a fresh cycle

Alice resolves the visible problem and sends a new exact Continue request for P1. Dalph verifies current task/revision/lifecycle/prerequisites/claim, W1/Git authority and old stopped writers, records distinct recovery authorization, then asks the agent to freshly verify W1 and return a new answer. This new cycle permits its initial response plus two full corrections. Alice sees the same P1/W1; the predecessor response is not silently reaccepted. Exact request redelivery returns recorded authorization/result and restart resumes its durable cycle without replenishing budget. Stale selection, changed authority or unproved custody refuses before provider effects. Acceptance seams: attempt-choice exact redelivery and claim tests extended to rejection recovery; fresh-verification/response and cycle-crash tests; public CLI/MCP recovery assertions.

Fresh provider startup can expose an incarnation process before it has an exact
thread identity. During S4 and S6, including rereading a retained terminal result through a fresh
provider incarnation, Dalph keeps the custody fence and performs at most
five read-only censuses, spaced by 100 ms and bounded by one second overall.
Only a complete fresh `Absent` result permits the successor intent. A still
unreadable census, a deadline, a live writer or contradictory identity refuses
Continue; Dalph neither ignores the process nor signals it. A crash during these
reads records no successor intent, so the original permission still reconciles
through the same stopped-writer boundary. The controlled tests in
`application/codex-recovery-census.test.ts` prove transient absence, persistent
uncertainty, live/contradictory refusal and a stalled-read deadline. The existing
native fresh-process Continue scenario proves composition with actual startup.

## S5 — Alice Restarts from fresh authority while keeping the predecessor

Alice requests Restart of the retained rejection, or of a historical Failed with unknown reason. Dalph reconciles exact old custody, current tracker specification/lifecycle/dependencies/claim and current Git Base H2, records distinct replacement authorization and plans P2 with its exact new W2 from H2. W1/candidate remain reference material. Lost append/response reconciliation reuses the recorded P2 rather than allocating P3. Alice sees predecessor and successor and their distinct Base/worktree facts. Unknown historical Failed offers Restart only; no Continue or retrospective acceptance changes its seal. Forbidden: stale Base, lost reference, replacement before old writer proof, new authority inferred from old terminal-invalidated choice. Acceptance seams: existing fresh-F2/K1/W1/H2 restart and ambiguous replacement tests extended to rejection and legacy unknown reason, public action availability.

## S6 — Dalph reconciles crashes and lost acknowledgements without extra turns

Crash cuts occur before/after durable correction intent, before/after turn/start acknowledgement, after turn observation, after validation and before/after durable outcome. On recovery Dalph reads the stored cycle and exact provider-owned turn/token before another request. An existing turn consumes its original remaining deadline and ordinal; an unresolved request outcome returns control to Alice without blind resend. A proven no-effect request may cross once under the same intent and remaining budget. Foreign claim/candidate, unreadable provider/Git facts and unproved stopped writers fail closed with retained work. Forbidden: retry from observation timeout alone, new budget on process restart, stale response acceptance or duplicated provider effects. Acceptance seams: controlled intent/ack/validation cut matrix, exact-turn reconciliation and unavailable-fact tests, model conformance plus negative controls.

## S7 — Dalph preserves terminal evidence and distinct later recovery direction

An earlier applied Stop/Restart is pending when an exact Accepted/Failed/Completed lifecycle report is accepted. That report becomes the current terminal fact under D48a; the earlier choice cannot replace or abandon it. Genuine provider/semantic failure retains Failed and an accepted candidate follows ordinary integration. Any separately allowed later recovery is a fresh explicit direction with its own exact request identity and current authority, preserving D49; it does not resurrect the invalidated choice or overwrite historical seals. Crash/redelivery returns the committed direction/result and does not reapply a competing choice. Alice sees the current terminal outcome and only admissible fresh actions. Acceptance seams: existing late-terminal Stop redelivery, Restart/Resume precedence tests and model D48a/D49 conformance extended with new recovery facts and stale-direction negative controls.

## Attached recovery commands

The listening host exposes `ApplyResultRecoveryDirection` and passive
`ReadResultRecoveryDirection`. CLI clients use:

```text
dalph attach recovery-apply --host http://127.0.0.1:43127 --run RUN --request-file /absolute/recovery.json --json
dalph attach recovery-read --host http://127.0.0.1:43127 --run RUN --request-file /absolute/recovery-id.json --json
```

`recovery.json` contains the exact `ApplyResultRecoveryRequest`: direction,
request ID, and selected report subject from current status. The read file
contains only that same `ResultRecoveryRequestId` (`nonce` and `runId`). MCP
uses `dalph_apply_result_recovery` with `{ runId, recovery }` and
`dalph_read_result_recovery` with `{ runId, recoveryRequestId }`.

An acknowledged direction returns `ResultRecoveryDirectionRecorded` with its
accepted journal cursor. This acknowledges direction, not completed recovery.
After an uncertain submission, Read returns that exact record or
`ResultRecoveryDirectionNotRecorded`; an unavailable reader remains an error,
never evidence that Apply had no effect. Neither client automatically resends
Apply. Fresh tracker/Git and writer proof still govern later execution.
