## #388 launcher mismatch and the first repair

The [#388 acceptance audit](ISSUE-386-ACCEPTANCE-AUDIT.md) records a completed hosted S1 workflow with CLI exit 1 at app-server close. Its separate wrapper probe recorded configured `codex-luna-max` but observed `node codex.js … app-server`; the original live run did **not** retain effective argv, so this is a reproduced compatibility defect, not a proven retroactive trace of that run. The original ad hoc diagnostic file under `/tmp` is no longer present locally; the retained audit and [#307 postmortem](postmortems/issue-307-qualification-churn.md) are the available evidence. The latter records a controlled probe and a passing `exec -a` variant.

The product [launch observer](../packages/dalph/src/application/codex-app-server.ts) checks expected executable, arguments, mode and process-start identity. Its [close path](../packages/dalph/src/application/codex-app-server.ts) rereads ownership and fails with `Ownership` before signalling a contradictory process. The current [production-live wrapper](../packages/dalph/src/qualification/live-qualification-runtime.ts) executes the locked `codex.js` with `exec -a "$0"`, preserving its wrapper locator as argv[0]. This is a fixture-specific compatibility fix; it does not justify relaxing the observer or signalling by PID alone. A custom wrapper with a different basename can still mismatch.

**First proposed repair (tooling only):** add one reusable launch-compatibility preflight in `packages/dalph/src/qualification/` and invoke it from `qualify:codex` before Vitest. It should start one disposable app-server using the *exact selected executable, arguments and environment*, then call the existing production ownership observer and close path. It must record configured executable, redacted effective argv, process-start identity, close result and stopped/retained custody as outside-Q qualification evidence. A mismatch or unreadable identity fails qualification; an ambiguous close retains the exact process locator for reconciliation. Reuse `CodexAppServer`/its native ownership service, not a new `spawn`/`kill` helper. This first step runs only in an opt-in verification command: the shipped CLI, production host, journal, task attempts and live qualification runtime cannot change. It needs no new Dalph runtime scenario.

**Next, separately accepted live change:** invoke that same preflight in the protected controller **before** a shipped Dalph task. The protected runtime currently creates the GitHub fixture before constructing its local wrapper, so the exact-wrapper probe belongs after local fixture construction and before shipped-child launch. Its failure must use the existing exact fixture cleanup and retention path. Before implementing this behavior change, accept a chronological qualification scenario: (1) Q has a pinned candidate, one created GitHub fixture and its exact local wrapper; (2) Q starts only the probe app-server with the selected wrapper and observes executable/argv/start identity; (3) an exact match closes under the current ownership service and permits the one shipped child; (4) a mismatch, unreadable identity or ambiguous close forbids that child, retains the probe locator and reconciles Q's existing fixture; (5) interruption before a conclusive close never becomes permission to retry a task mutation. Map those outcomes to controlled tests and the existing [protected live qualification matrix](DEVELOPMENT.md#protected-disposable-live-qualification). No matcher relaxation or alternate process manager is part of the scenario.

Focused proof for that step: [app-server process policy tests](../packages/dalph/src/application/codex-app-server-process-policy.property.test.ts) and [production-live wrapper tests](../scripts/run-production-live-qualification.test.mjs), plus a controlled exact-wrapper pass and mismatched-wrapper rejection. The preflight must not replace #388's hosted S1 evidence or weaken the production-live fail-closed behavior.

## Migration order and stop rules

1. **High churn, small change:** add the shared launch-compatibility preflight above and wire direct `qualify:codex`; accept the live chronology above before wiring the protected controller. Preserve the production wrapper, exact ownership observer, and no-retry live controller. Stop after focused wrapper/ownership tests and a controlled local preflight; no hosted S1 or broad gate is needed for this audit.
2. **Medium churn, verification custody:** make `qualify-codex-app-server.mjs` and delivery warm mode use the existing bounded verification process owner for deadline, signal relay, retained logs and stopped-child proof. Keep their test selection and occurrence assertions. Touch [`run-delivery-repeatability.test.ts`](../scripts/run-delivery-repeatability.test.ts) and gate custody tests only for boundaries actually changed; a tooling-only change cannot affect Dalph task behavior.
3. **Low churn, CI layout:** separate pure provenance/manifest logic from the protected live one-shot adapter, preserving the same manifest and retention schema. Keep hosted quality/formal stage adapters and gate status/reconcile commands. Remove an adapter only after its `package.json`/workflow caller is eliminated; there is no evidence to delete any current substantial driver now.

The only proposed new Effect service/command is the qualification launch preflight extracted into `packages/dalph/src/qualification/` and composed with the existing Codex app-server Layer. The existing protected live Effect runtime already owns its fixture and shipped task; no standalone script should be migrated wholesale into the task workflow. The abandoned one-off #388 process probe stays deleted. The initial direct-qualification and verification-custody changes are tooling-only. The later live preflight requires the chronology above because it changes Q's setup sequence, while leaving accepted S1–S8 task behavior and the [#388 hosted S1 result](scenarios/direct-remote-publication.md) intact. Product process-policy changes would reopen those scenarios before code.

After these steps, gate children have one owner (`run-bounded-command` under admitted custody), while live task children have one owner (`CodexAppServer` and its Effect process/cleanup services). The CI adapter may launch exactly one controller but cannot decide task recovery. Gate receipts and formal reports remain outside the Dalph journal; the journal owns workflow history, Git owns refs/worktrees, and the execution substrate owns process observations. A deadline or ambiguous outcome must remain with its respective owner until exact stopped/observed evidence exists. This boundary preserves both the #388 no-blind-retry rule and production-live fail-closed cleanup.
