# #360 installed-input and observation seam

When a developer repeats the complete formal command, the saved success can be reused only if the currently installed checker and runtime bytes are identified and observed before enumeration through qualification. A same-version replacement of a loaded system library must invalidate that success. An undeclared external link or unsupported runtime configuration must refuse checker launch.

This is read-only seam research plus this report; it changes no Dalph runtime or verification command behavior. No checker/server launch, installation, feature edit, or acceptance test was performed by this analysis. Sources are the integration worktree scripts and installed Quint 0.32.0 source, and the approved [#357 contract](https://github.com/dearlordylord/dalph/issues/357#issuecomment-5649197858) and [#360 scenarios](https://github.com/dearlordylord/dalph/issues/360). Installation was initially absent and became visible during analysis; visibility is not an installation-coherence qualification.

## Existing reuse and holes

`gate-resume-inputs.mjs` already freshly walks membership, modes, contents and resolved links, records optional absence, establishes the observer before its snapshot, drains it and compares a final complete snapshot. `gate-input-observer.py` watches ancestors, membership before descendants, authored links and their resolved targets; overflow, unmount, watch removal and errors fail. These are useful narrow primitives, not a completed formal layout.

The existing layout hardcodes the entire worktree, HEAD/index and Git authority inputs. Reusing that layout directly contradicts formal applicability after unrelated application or HEAD/index changes. Its walker visits arbitrary resolved symlink targets and treats already-visited paths as complete: it does not reject directory-link cycles or undeclared external targets. The observer likewise follows arbitrary resolved links. Both require a common declared-root/link policy before claiming the stronger formal contract. A global visited set must distinguish benign repeated dependencies from a cycle in the active traversal chain; pnpm packages can have dependency graph cycles without an infinitely traversed filesystem directory-link cycle.

Existing tools cover the Node executable, Python/Git executables, declared launchers and pnpm implementation package root, but not complete runtime dependencies. `readQuintEvaluatorProvenance` hashes Rust evaluator bytes and reports versions/platform/architecture; it does not identify dynamic dependencies. `getRustEvaluatorPath` downloads on absence. Quint `fetchApalache` downloads if the launcher is absent. Preparation must therefore precede observation, and the guard must require complete prepared artifacts; the current cold-check preparation inside `check-quint-models.mjs` cannot remain hidden guarded work.

## Concrete runtime evidence

Read-only `ldd` inspection on this Linux arm64 host found Node loading `/lib/aarch64-linux-gnu/{libdl,libstdc++,libm,libgcc_s,libpthread,libc}` plus `/lib/ld-linux-aarch64.so.1`. Java's launcher loads JRE `lib/libjli.so` plus system libraries; a launcher-only inspection does not include the subsequently loaded JVM and its configuration-dependent modules. Rust evaluator v0.6.0 loads libgcc_s, libm, libc and the same loader. Thus hashing only executables/JARs is demonstrably insufficient.

The complete JRE is about 137 MiB; pnpm implementation about 20 MiB; Apalache 0.56.1 distribution about 130 MiB; the host architecture system-library tree about 385 MiB (`du -sh`, approximate storage sizes, not timing measurements). Quint's installed package imports transitive npm dependencies outside its own package directory. Traversing its surrounding pnpm package dependency links is necessary; hashing a version or lockfile is insufficient. Full worktree node_modules can conservatively include them but also hashes application-only dependencies and contains workspace links; selecting a general transitive closure engine is expressly excluded.

## Conservative roots versus a dynamic closure

A sampled `/proc/<pid>/maps` or `ldd` output proves specific loaded files, not all effective inputs for the complete profile. Conditional dlopen, locale/timezone/name-service/configuration files and loader redirects remain gaps. A dynamic trace-driven dependency discovery system would be substantial new infrastructure and is not narrow walker reuse.

A possible narrow supported-host policy instead explicitly declares complete Node installation, pnpm implementation, complete prepared Quint installation dependency roots, complete JRE and Apalache distribution, evaluator installation, loader/system-runtime trees and necessary configuration/data roots. It strips unsupported loader/Java/Node configuration overrides before child execution, or rejects them with their concrete cause; every retained caller-controlled value is digested including unset versus empty. Every external target must fall within declared roots. This is conservative identification, not a minimal dynamic closure. Its sufficiency needs an explicit supported-platform/configuration policy and controlled negative tests, and its hashing/watch cost must be measured. Declaring system library roots alone is not yet proof that locale/timezone/runtime configuration inputs are covered. General /etc or /usr observation also risks unsupported kinds and unrelated writes; do not silently expand to entire host trees or exclude troublesome effective files.

The limiting seam is complete runtime/configuration coverage plus installed pnpm dependency coherence, not filesystem hashing itself. No current evidence proves a complete bounded declared-root policy. If proving it requires general runtime dependency discovery, portable observation, broad environment repair or a server-management subsystem, #360 requires reporting the scope/cost and stopping before feature buildout.

## Smallest proposed controlled probe

Wait for the installation owner to report readiness. Do not launch from a partly populated installation. Preselect a 30-second outer guard for a disposable installed-input fixture and a separate 60-second outer guard for one minimal real-tool preparation/identity probe, each including at most 5-second termination plus 2-second absence accounting; no automatic retry or deadline increase. These are experiment watchdogs, not changes to the accepted execution policy.

First use a disposable declared tool tree with a launcher, transitive dependency link, runtime library and optional config. Establish the existing observer before enumeration. With readiness barriers, replace library bytes under the same version, edit/revert, create/delete, replace a link and alter mode. Assert identity changes between invocations and sticky observation rejection during qualification. Add undeclared external target, active link cycle, unreadable file, unsupported kind, missing required runtime and observer-loss negative controls; assert zero checker launches. Prove benign repeated dependency links remain coherent.

Then perform one guarded prepared-installation inventory/observer setup, without executing the full profile. Enumerate complete proposed roots and resolved targets, count bytes/paths/watches and measure setup, hashing and final qualification. Inspect Node/pnpm/Quint resolution and prepared Java/Rust/Apalache paths against that inventory. A minimal real typecheck/evaluator/owned-server probe belongs to the coordinated execution seam, only after this policy can identify its inputs. Loading a file observed in a trace is corroboration, never proof that all profile paths are identified.

Scenario-to-test mapping: S5 -> `invalidates changed effective tools environment profile or policy` and `refuses unidentifiable current inputs`; S7 -> `rejects edit and revert at every qualification phase` and `fails closed on incomplete observation`; S3/S4 -> `reruns after input membership content mode or link changes` and standalone unrelated-edit applicability; S13 -> `unsupported prerequisites never yield verified success`. All are proposed/not run here. S1/S2 and real release measurements remain blocked on complete input coverage and the other #360 seams; this report does not narrow their requirements.

Its sole undeclared target was the reducer-lab workspace application link; this root design was rejected as unnecessarily including unrelated application inputs.

The distinguishing design starts at the installed Quint package's containing `node_modules`, follows only naturally encountered links, permits targets within the pnpm store without enumerating the store wholesale, and never ascends to parent directories. Including the complete Python standard library produced 17,866 files, 2,787 directories, 1,052,852,682 apparent bytes and 1,314 links in 1.42 seconds. No cycles, unsupported kinds or read errors occurred. One additional external link was `/usr/lib/python3.11/sitecustomize.py` -> `/etc/python3.11/sitecustomize.py`; the proposed roots now include `/etc/python3.11`. These timings are enumeration only, not hashing or observer qualification, and do not prove complete runtime-policy coverage. The host's inotify user watch and instance limits both report 1,048,576.

Scratch evidence: `.scratch/formal-reuse-probes/input-inventory.{py,json}` and `input-narrow-inventory.{py,json}`. The first attempted observation/hash harness failed at Node module resolution because its relative observer import ascended one directory too far. No observer or checker launched and no observation timing was obtained. This was reported before any retry; the 60-second experimental guard was not increased.

## Input-policy implementation handoff

`formal-input-policy.mjs` now provides the clean caller environment, prepared tool resolution and observed formal guard. The environment keeps only explicitly supported PATH/home/tool settings, memory/GC arguments, locale/timezone/temp settings and pnpm launcher identity; other ambient and lifecycle fields are stripped. Unsupported loader, Node, Java or external configuration overrides refuse work. Runner-owned custody/server/report fields must be supplied afterward by the admitted caller and cannot be authored as arbitrary caller environment identity exclusions.

The prepared resolver requires pinned project pnpm/Quint, this worktree's pnpm installation, nonempty executable evaluator and prepared launcher/JAR, complete identified Node/JRE and Debian Python runtime. Its finite Debian-12 Linux arm64/x64 root policy follows the containing Quint package node_modules and its naturally reached dependency links. It refuses Node installations whose inferred directory would be the entire /usr or /usr/local, and custom unidentified Python. It identifies host using hostname plus machine-id digest. Loader redirects, active external OpenSSL includes/provider modules and unsupported passwd/group/hosts name-service sources are refused again after observation starts and during final qualification, preventing a root-resolution/setup gap from accepting a changed configuration.

The filesystem manifests freshly record modes, contents, membership, absence and link target/resolved locations, reject unsupported kinds, inaccessible inputs, active cycles and undeclared targets, and exclude HEAD/index/base/application source from formal identity. Source-model import locators outside declared formal roots refuse work. The guard observes before enumeration, drains before and after final hashing, checks caller profile/environment/toolchain mutation, and retains sticky failures. Setup and qualification have finite millisecond budgets. Shared observer options add bounded timeout/cancellation and an isolated, clean Python environment; defaults retain the existing quality-guard behavior and repeated close calls await the same terminal helper cleanup.

Scenario evidence: S3 -> `reruns after input membership content mode or link changes`; S4 -> `retains formal reuse across unrelated edits without binding HEAD index or base`; S5 -> `invalidates changed effective tools environment profile or policy`, `refuses unidentifiable current inputs: undeclared target and cycle`, `unreadable current inputs refuse qualification without a hash fallback`, `rejects a Quint import outside the conservative formal boundary`; S7 -> the three `rejects edit and revert at qualification` tests plus `fails closed on lost observation and supports bounded abort`; S13 -> `unsupported prerequisites never yield verified success` and clean-environment override rejection. ## Review repair: authored Quint import sources

The specification reviewer reproduced a P1 input-coverage defect: the original line-based regular expression missed a valid multiline `import ... from` declaration, and comment stripping could hide `//` inside a quoted locator. This was accepted as a blocker because a checker could consume an external unobserved model before the policy refused it.

The repair uses the pinned installed Quint parser's `parsePhase1fromText` and `newIdGenerator`; every module's import and instance declaration is inspected. The pinned `fileSourceResolver.lookupPath` computes the exact locator the checker uses, including raw escape treatment and the unconditional `.qnt` suffix. No handwritten syntax or comment regular expression remains. Syntax errors refuse identification rather than silently treating a source as having no imports. Both initial and final guarded snapshots perform this validation.

S5 coverage now includes `parser rejects external imports: multiline source declaration`, `comment-like quoted source`, `escaped quoted source`, and `module instance source`. Positive controls `parser respects comments and quoted strings without manufacturing source imports` and `parser validates an observed multiline local import using checker locator semantics` prove valid observed inputs remain usable. The affected focused suite passes 19/19; formatting and whitespace checks pass. No checker process runs to parse these inputs. Independent reviewer revalidation was requested after the repair.

## Review repair: implicit Apalache configuration discovery

The specification reviewer confirmed a second P1 against the actual pinned JAR: Apalache ConfigManager reads `System.getProperty("user.home")/.tlaplus/apalache.cfg` and searches the working directory and every parent for `.apalache.cfg`. Caller HOME is not proof of JVM user.home. Omitting these paths could reuse old success while a fresh server would consume newly created, malformed or behavior-changing configuration. This finding was accepted.

The resolver now runs only the already identified Java executable with bounded `-XshowSettings:properties -version` before observation, requires one absolute actual user.home property, includes `javaUserHome` and concrete `configPaths` in toolchain identity, and adds enforced `-Duser.home=<identified home>` to owned Java arguments. This no-server identification call succeeded here with `/home/node`. The guard independently computes the actual-home configuration and all working-directory ancestor configurations, observes their paths before enumeration, records their absence and refuses any presence in both initial and final snapshots. It does not parse HOCON or permit external include discovery. Parent/server ownership ensures the same exact Java/home setting is enforced in TLC children too.

S5/S13 tests `refuses implicit Apalache configuration at worktree`, `ancestor`, and `JVM user.home` reject present malformed configuration. S7 test `observes absence of implicit Apalache configurations and rejects ordinary create revert` proves restored absence cannot hide a during-invocation change. `JVM configuration paths bind actual identified home instead of caller HOME` proves caller HOME's unrelated config cannot substitute for actual JVM coverage, then rejects creation at the actual home. All 24 focused input-policy tests pass. The earlier parser repair was independently accepted by the specification reviewer; independent recheck of this config repair was requested via parent after direct agent messaging reached the thread limit.
