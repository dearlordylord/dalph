# SwarmForge reliability architecture

## 1. Scope, pins, and evidence boundary

- Repository: `unclebob/swarm-forge`.
- Fixed-role pin: [`main@9acd54d2239fef7e41ddacd8fd30dfb0e69672fe`](https://github.com/unclebob/swarm-forge/tree/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe). At this pin `main` describes itself as documentary/shared machinery; runnable pack branches supply role prompts and configuration ([README, lines 9-19](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/README.md#L9-L19)).
- Squad pin: [`squad@b13d8ce1d5f9b3b4591a53261a8226c0c781803b`](https://github.com/unclebob/swarm-forge/tree/b13d8ce1d5f9b3b4591a53261a8226c0c781803b). This later branch contains the fixed-role machinery plus a persistent squad leader, short-lived role-template workers, a daemon, dashboard, approvals, assignments, packets, merge handling, and recovery helpers ([README, lines 252-295](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/README.md#L252-L295), [test runner, lines 1-42](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/test/swarmforge/test_runner.clj#L1-L42)).
- Evaluation assumption: one local project directory and one intended `squadd` process on the squad branch. The file locks coordinate same-host helper processes; this audit does not assume shared-filesystem multi-host safety.
- Evidence boundary: reachable source and tests at both commits. Documentation is used only to describe stated product intent. No live provider call, kill experiment, remote integration experiment, or week-long drift experiment was run.

The squad branch is not credited with exact restoration merely because its files are durable. The source separately establishes which facts are written, which processes remain only in tmux, and which recovery decisions are reconstructed from current Git and filesystem observations.

## 2. Plain-language architecture

### `main`: fixed roles and handoff files

An operator starts a configured swarm in a local Git repository. Startup reads the role rows, creates one branch/worktree for each non-main role at the root checkout's then-current `HEAD`, creates one tmux session per role, copies helper scripts into each worktree, and launches the chosen CLI there. Existing role worktrees are reused, but existing tmux sessions are killed and replaced ([launcher, lines 242-286](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L242-L286), [launcher, lines 505-550](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L505-L550)).

When a role finishes work, the person represented by that role asks the helper to queue either a note or a Git commit handoff. The helper validates a ten-character commit abbreviation, resolves it to one commit, generates a sortable ID, and atomically publishes the message into that worktree's outbox ([handoff writer, lines 157-234](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarm_handoff.bb#L157-L234), [handoff writer, lines 240-292](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarm_handoff.bb#L240-L292)). A daemon copies the file into each recipient's inbox, tries to wake the recipient through tmux, and then moves the sender copy to `sent`; an exception instead moves it to `failed` ([handoff daemon, lines 85-144](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/handoffd.bb#L85-L144), [handoff daemon, lines 164-178](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/handoffd.bb#L164-L178)).

The recipient claims the lexically first file from `new` by moving it to `in_process`. If a current file already exists, `ready_for_next` returns that same file; `done_with_current` timestamps it, moves it to `completed`, and then looks for another item ([ready helper, lines 90-118](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/ready_for_next_task.bb#L90-L118), [done helper, lines 68-93](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/done_with_current_task.bb#L68-L93)). Git integration is not performed by that transport: the generated body tells the recipient agent to `merge_and_process` the sender commit ([handoff writer, lines 265-292](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarm_handoff.bb#L265-L292)).

### `squad`: durable local workflow plus transient workers

An operator or the squad leader first records themes, stories, artifacts, gates, and assignments under `.squad`. Assignment creation freezes a rendered assignment, metadata, initial status, a result-handoff draft, and a theme event; optionally it writes a durable spawn request ([assignment creation, lines 401-514](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L401-L514), [spawn request, lines 525-589](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L525-L589)).

On each poll, `squadd` derives deterministic mechanical actions from those files, applies bookkeeping, retirement, capacity-scheduled assignment/spawn/approval actions, handoff claims, merge checks and accepts, then leaves judgment, approval, and recovery decisions for the visible squad leader ([action authority, lines 9-38](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_actions.clj#L9-L38), [mechanical pass, lines 2845-2888](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_next.clj#L2845-L2888), [daemon poll, lines 1157-1202](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L1157-L1202)).

For a spawn request, a helper creates a dedicated branch and worktree from the root's current `HEAD`, copies a frozen prompt and launch script, writes agent metadata/status/heartbeat, registers the role, and starts a detached tmux session ([spawn, lines 505-575](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L505-L575), [spawn, lines 585-624](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L585-L624)). A worker returns a validated Git handoff. The daemon records the result commit, dry-runs a merge in a detached worktree, and—if still clean—merges locally into the current root checkout and records the resulting local `HEAD` ([result validation, lines 769-876](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L769-L876), [merge check, lines 1193-1232](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L1193-L1232), [accept, lines 1438-1499](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L1438-L1499)).

## 4. Scheduling and capacity

On `main`, every configured role starts. Startup adds a configurable delay between CLI launches, but there is no task admission or dynamic execution cap; queue order is the handoff filename's priority/timestamp/sequence order and each role has one task or one equal-priority batch in process ([launcher, lines 529-539](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L529-L539), [ready helper, lines 17-31](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/ready_for_next_task.bb#L17-L31)).

On `squad`, `max_transient_agents`, per-template caps, grouped caps, and a merger singleton constrain transient workers. Active counts normally require a live tmux session and exclude a `handoff_sent` worker whose handoff is already visible; test/no-launch mode instead uses status ([squad config, lines 1-49](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/squad.conf#L1-L49), [spawn counts, lines 93-149](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L93-L149), [spawn limits, lines 185-233](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L185-L233)).

The apparent count-then-create race is closed for ordinary helper callers: `squad_spawn` acquires `.swarmforge/squad/spawn.lock`, rereads the role registry, checks task occupancy and capacity, then keeps the lock through worktree creation, registration and launch; retirement uses that same lock ([spawn, lines 599-624](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L599-L624), [retire, lines 230-267](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_retire.clj#L230-L267)). This establishes same-host serialization, not a distributed reservation: a hard-dead owner leaves a stale directory that a later workflow pass proposes deleting, and direct external mutations do not participate ([next action, lines 2206-2231](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_next.clj#L2206-L2231)).

Ready workflow candidates are sorted by priority, theme, stage, story and assignment. The planner projects several independent actions, accounts for capacity and dependency conflicts, and applies registry-mutating retirements one at a time; daemon polls repeatedly drain successful mechanical work ([candidate order, lines 2548-2555](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_next.clj#L2548-L2555), [retirement, lines 2413-2451](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_next.clj#L2413-L2451), [daemon loop, lines 1181-1208](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L1181-L1208)).

## 5. Restoration layers

### Control-plane task and run

`main` durably restores handoff queue position only. Directory moves encode queued, current and completed work, and the helper fails on multiple current items instead of guessing ([ready helper, lines 90-118](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/ready_for_next_task.bb#L90-L118)). It has no separately modeled run/attempt identity, dependency graph, approval state or completion result beyond these handoffs.

`squad` restores themes, numbered story references, story packets, approvals, assignments, results, merge state, blockers, agents and spawn queue states from `.squad` files. Most snapshots use temp-file rename; event lines are separate appends ([theme writes, lines 83-121](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_theme.clj#L83-L121), [packet writes, lines 201-214](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_packet.clj#L201-L214), [assignment writes, lines 501-514](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L501-L514)). This is replayable projection state, not an atomic effect journal: for example an assignment is written before its spawn request, and a spawn request is moved to `in_process` before the helper performs all creation effects ([assignment/spawn request, lines 551-589](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L551-L589), [daemon spawn, lines 1082-1101](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L1082-L1101)).

### Agent session, context, and logs

If the host and tmux server remain alive, both branches preserve the same live CLI process, its in-memory context and tmux scrollback even when a terminal window closes; the window watchdog reopens a non-cleanup surface onto the same tmux session ([README, lines 374-380](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/README.md#L374-L380)).

If that process is gone, neither launch path supplies a provider resume/session handle. `main` invokes a fresh CLI from role instructions; squad invokes a frozen launch script and has metadata for backend/session/worktree but no provider conversation ID ([main launch, lines 323-349](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L323-L349), [squad launch, lines 287-327](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L287-L327), [squad metadata, lines 391-402](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L391-L402)). Squad's liveness file contains only the last ten pane lines, a hash and observation fields, while handoff/event files preserve workflow evidence rather than the full chat ([daemon liveness, lines 496-516](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L496-L516)).

### Complete Git/worktree state

While a role worktree remains on disk, Git itself preserves commits, staged entries, unstaged edits, untracked and ignored files, conflicts and stashes. Neither branch serializes those layers into control-plane records. `main` simply reuses an existing worktree; a new one is created/reset to a role branch at root `HEAD` ([main worktrees, lines 251-259](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L251-L259)).

Squad recovery enumerates tracked/staged/unstaged/untracked status through `git status --porcelain=v1 --untracked-files=all`, so these visible dirty layers prevent automatic “no work” classification. It does not request ignored files, stash state, conflict metadata or a tree/index fingerprint ([recovery, lines 55-69](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_recover.clj#L55-L69), [recovery rules, lines 153-202](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_recover.clj#L153-L202)). The test establishes untracked-file protection, not complete Git-layer inventory ([recovery test, lines 8-35](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/test/swarmforge/recover_test.clj#L8-L35)).

Retirement deliberately destroys the managed worktree with `git worktree remove --force`, falls back to deleting its directory, and force-deletes the branch after the assignment handoff reaches one of the accepted terminal states ([retire gate, lines 197-228](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_retire.clj#L197-L228), [retire cleanup, lines 120-157](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_retire.clj#L120-L157)). Therefore any ignored, stashed or otherwise unmerged state is recoverable only before retirement; the cleanup result is logged but is not disposition-typed by Git layer.

### Live process, container, or VM state

The execution substrate is a local tmux session running a host CLI. The squad daemon detects missing sessions, dead panes and unchanged pane tails and alerts the squad leader; recovery classifies but does not reattach/relaunch a vanished process ([daemon, lines 480-591](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L480-L591), [recovery, lines 186-235](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_recover.clj#L186-L235)). No product-owned container, VM snapshot, PID namespace, process-group inventory or child-process adoption path appears at either pin.

## 6. Immediate restart

### Coordinator/daemon restart while tmux survives

On `main`, a replacement handoff daemon rereads roles and outbox files each poll. A file still in outbox is retried; an inbox file remains claimable; an `in_process` file is returned as the current task. Delivery is at-least-once by file presence rather than one atomic broadcast occurrence: recipient copies are written before wakeup and before the sender file moves to `sent`, so a crash can leave some copies installed and the source still retryable; existing target filenames suppress rewriting ([daemon delivery, lines 123-144](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/handoffd.bb#L123-L144), [ready helper, lines 97-118](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/ready_for_next_task.bb#L97-L118)).

On `squad`, restarting `squadd` reloads `.squad`, repairs missing `roles.tsv` rows from agent metadata, drains deterministic actions, scans spawn requests, deliveries and status, and continues to use the same tmux sessions ([daemon reconcile, lines 268-283](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L268-L283), [daemon loop, lines 1181-1202](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L1181-L1202)). ### Full local swarm restart

Rerunning `main` kills any known existing sessions, retains existing worktree directories, and launches fresh CLI processes; it does not restore old agent conversations ([launcher, lines 515-539](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L515-L539)). ## 7. Restart after a week and external drift

If the project directory and `.git` survive for a week, both branches retain worktrees and handoff files. Squad additionally retains the complete file-backed workflow projections and frozen worker instructions. If tmux or the host rebooted, live model/process context is gone and squad can only classify the surviving files and Git state ([spawn metadata, lines 391-402](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L391-L402), [recovery context, lines 208-235](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_recover.clj#L208-L235)).

The strongest week-later drift defect is the worker base. Spawn creates the branch from root `HEAD`, but the agent metadata does not persist that resolved SHA. Recovery later resolves the root checkout's *current* `HEAD` and counts `<current-root-HEAD>..worker-HEAD` ([spawn, lines 505-535](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L505-L535), [metadata, lines 391-402](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L391-L402), [recovery, lines 63-69](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_recover.clj#L63-L69)). Source establishes the moving comparison; it is an inference that later root integrations can make `COMMITS_AHEAD` under- or over-describe the worker's progress relative to its actual start.

There is no remote reconciliation layer. Local branches, the root checkout and abbreviated result/merge SHAs may still exist, but force-pushed/deleted remote refs, a changed target head, PR state, credentials, installed CLI version, model, tool cache and OS dependencies are neither frozen nor re-read as an integration protocol. The worker launch freezes backend name, assignment and paths, while executable resolution remains through current `PATH` and CLI names ([spawn launch script, lines 317-327](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L317-L327), [daemon spawn environment, lines 1027-1044](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L1027-L1044)).

## 8. Git starting-point and integration behavior

`main` creates each missing role worktree with `git worktree add --force -B swarmforge-<name> <path> HEAD`; it records neither that resolved starting SHA nor one worktree per task attempt. A fixed role's worktree/branch is reused across successive handoffs ([main worktrees, lines 251-259](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L251-L259)). Squad gives each transient worker its own branch/worktree, also based on then-current root `HEAD`. A result is accepted only as a ten-character commit; when the sender branch exists, the commit must be reachable from it ([spawn, lines 505-535](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_spawn.clj#L505-L535), [result reachability, lines 822-862](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L822-L862)). A daemon-owned local PID/file lock serializes merge-ready checks and accepts. Readiness merges into an isolated worktree made from current root `HEAD`; acceptance rechecks tracked cleanliness and either recognizes the result as already reachable or runs a local `--no-ff` merge ([merge ownership, lines 1029-1123](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L1029-L1123), [dry run, lines 1193-1232](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L1193-L1232), [accept, lines 1474-1499](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L1474-L1499)).

This is a useful single-local-writer integration kernel, not a remote target protocol. It stores result commit and resulting local merge commit, but no planned Base SHA, target-ref/head observation, tested-result identity beyond the dry run, push intent/result, PR, accepted remote head, or reconcile-before-retry occurrence. ## 13. Maintenance risks

- **Two architectures under one name:** `main` is fixed-role handoff transport; `squad` is a much larger workflow controller. Conclusions must always name the branch ([main README, lines 9-19](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/README.md#L9-L19), [squad README, lines 252-295](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/README.md#L252-L295)).
- **Flat-file connascence:** packet fields, assignment status, accepted merge, approvals, handoff directories, agent state and event logs encode related lifecycle facts in separate files/writes ([packet fields/write, lines 145-210](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_packet.clj#L145-L210), [assignment merge writes, lines 986-1005](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L986-L1005)).

## 16. Technical and user-visible consequences

At `main`, users get a transparent local workspace per role, live tmux observability, and handoff files that survive daemon or terminal-window failure. If an agent restarts, it can see the exact current inbox item and the worktree still holds Git/filesystem progress. Users do not get durable task attempts, capacity control, exact bases, provider-context restoration, or control-plane-owned integration; correctness after a mid-merge failure depends on inspecting Git and instructing a fresh agent ([ready helper, lines 90-118](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/ready_for_next_task.bb#L90-L118), [main launch, lines 323-349](https://github.com/unclebob/swarm-forge/blob/9acd54d2239fef7e41ddacd8fd30dfb0e69672fe/swarmforge/scripts/swarmforge.bb#L323-L349)).

At `squad`, users additionally get durable assignments/gates/packets, bounded transient workers, a dashboard-facing workflow, daemon-owned local merge serialization, conflict-specific merger work, conservative dirty-work recovery and seeded workflow simulation. A daemon restart can usually continue from the files without relaunching healthy workers, and local ancestry can reconcile a merge whose record was missed ([daemon poll, lines 1157-1202](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squadd.clj#L1157-L1202), [merge/record, lines 1438-1497](https://github.com/unclebob/swarm-forge/blob/b13d8ce1d5f9b3b4591a53261a8226c0c781803b/swarmforge/scripts/squad_assign.clj#L1438-L1497)).

Those guarantees stop at the local host and surviving worktree. A worker lost after a reboot cannot resume its exact conversation; an `in_process` spawn request can strand; recovery judges commits against a moving root `HEAD`; retirement can erase un-inventoried Git layers; and local merge success says nothing about a remote target or accepted head. Technically, SwarmForge squad is a substantial file-backed local workflow controller with strong same-host operator visibility, not an exact-attempt, remote-authority delivery control plane.

For Dalph, the comparative result is narrower: borrow Swarm Forge's habit of
showing the concrete actor, action, and boundary before mechanism names, but
import no orchestration mechanism now. A named missing fault history may be
added to Dalph's existing cassette, property, model, or recovery-prefix seam;
it does not justify a second generic simulator. Durable transport spools or
human approval requests need their own accepted boundary design if a future
product requirement calls for them. Dalph already owns stronger exact-attempt,
capacity, authority-separation, ambiguity-reconciliation, preservation,
cleanup, and accepted-head integration protocols than the corresponding local
Swarm Forge mechanisms.
